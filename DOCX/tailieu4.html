Authentication & Accounts

Xác thực người dùng, bảo mật mật khẩu, quản lý phiên

🗄️ Database & Server Layer
A Thiết kế Database Schema

SQLite cần quản lý hai thực thể chính: Người dùng (users) và Phiên làm việc (sessions).

SQL
-- Bảng lưu trữ thông tin người dùng
CREATE TABLE users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- Bảng quản lý phiên đăng nhập (phục vụ xác thực và auto-login)
CREATE TABLE sessions (
    session_token TEXT PRIMARY KEY,
    user_id       INTEGER NOT NULL,
    expires_at    DATETIME NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
⚠️
Lưu ý: username được thiết lập thuộc tính UNIQUE ở tầng database để ngăn đăng ký trùng tên, tránh Race Condition khi có nhiều request đồng thời.
B Tích hợp Argon2 qua Libsodium & vcpkg

Thay vì dùng MD5 hay SHA-256 (dễ bị tấn công brute-force bằng GPU), hệ thống tích hợp Argon2id thông qua Libsodium.

🔐 Khi Đăng ký
Mật khẩu thô qua crypto_pwhash_str — tự tạo salt ngẫu nhiên, cấu hình memory/time cost, tạo chuỗi hash an toàn $argon2id$...
✅ Khi Đăng nhập
Dùng crypto_pwhash_str_verify để so sánh mật khẩu thô với hash — Libsodium tự giải mã cấu hình salt mà không cần lưu salt riêng.
C Control Channel & Cấu trúc Ready Payload

Tất cả lệnh điều khiển (Auth, Join Server, Create Channel) đều đi qua Control Channel — kết nối Socket hướng sự kiện.

1

Register Flow: Client gửi auth.register → UserHandler kiểm tra username → Hash mật khẩu Libsodium → INSERT vào DB → Trả kết quả.

2

Login Flow: Client gửi auth.login → Xác thực crypto_pwhash_str_verify → Sinh session_token (UUID/Hex) → Lưu vào bảng sessions (30 ngày) → Trả ready_payload.

📦 JSON — ready_payload structure
{
  "event": "auth.ready",
  "data": {
    "session_token": "ss_9a8b7c6d5e...",
    "user": { "id": 14, "username": "nguyenvanA" },
    "servers": [{
      "id": 101, "name": "Học Tập C++",
      "channels": [
        { "id": 501, "name": "thao-luan-chung", "type": "text" }
      ]
    }]
  }
}
Ý nghĩa Ready Payload: Client có ngay "bản đồ" dữ liệu đầy đủ để vẽ UI khi vừa đăng nhập xong, giảm thiểu tối đa số round-trip lên server.
🖥️ UI & Client Layer
A Màn hình Login / Register
🔄 Toggle
Màn hình mặc định là Login. Có nút chuyển đổi sang Register và ngược lại.
✔️ Validation
Kiểm tra độ dài mật khẩu >6 ký tự, username không có ký tự đặc biệt trước khi gửi lên server.
🚫 Anti-Spam
Disable nút bấm khi đang đợi Server phản hồi, tránh spam click gửi nhiều request trùng.
B Lưu trữ Session & Auto-Login
1

Khởi động app → kiểm tra session_token trong bộ nhớ cục bộ.

2

Nếu CÓ: gửi auth.verify_session qua Control Channel thay vì hiển thị màn hình Login.

3

Server kiểm tra bảng sessions → hợp lệ: trả về ready_payload → vào app. Hết hạn: xóa token, hiển thị Login.

Servers & Channels

Quản lý máy chủ, kênh, thành viên và định tuyến tin nhắn

🗄️ Database & Server Layer
A Database Schema

Mô hình: 1 Server → nhiều Channel; N User ↔ N Server (quan hệ nhiều-nhiều).

SQL
CREATE TABLE servers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL, owner_id INTEGER NOT NULL,
    icon_url TEXT, created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (owner_id) REFERENCES users(id)
);

CREATE TABLE channels (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    server_id INTEGER NOT NULL, name TEXT NOT NULL,
    type TEXT CHECK(type IN ('text', 'voice')) NOT NULL DEFAULT 'text',
    FOREIGN KEY (server_id) REFERENCES servers(id) ON DELETE CASCADE
);

-- Bảng trung gian N-N
CREATE TABLE server_memberships (
    server_id INTEGER, user_id INTEGER,
    joined_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (server_id, user_id)
);
B Targeted Routing — Thay thế Broadcast toàn cục

Thay vì phun dữ liệu tới tất cả socket (lãng phí băng thông, vi phạm bảo mật), hệ thống dùng cấu trúc In-memory để định tuyến chính xác.

C++
// key: channel_id → danh sách kết nối mạng trong kênh đó
std::unordered_map<int, std::set<ConnectionPtr>> channel_routing_map;
1

Gửi: Client gửi gói tin kèm channel_id và content.

2

Xác thực quyền từ DB: Kiểm tra server_memberships để đảm bảo user có quyền.

3

Định tuyến trên RAM: Tra channel_routing_map → chỉ push dữ liệu tới đúng các kết nối trong kênh đó.

🖥️ UI & Client Layer
A Left Server Rail
⬤ Active State
Vệt sáng màu trắng ở mép trái, icon Server nổi bật.
🔴 Unread State
Chấm thông báo nhỏ hoặc hiệu ứng mờ khi có tin nhắn chưa đọc.
💬 Tooltip
Hover chuột hiển thị tên đầy đủ của Server.
B Channel List

Phân chia thành 2 nhóm: # Text Channels (văn bản) và 🔊 Voice Channels (âm thanh). Click Text Channel tải lịch sử tin nhắn; click Voice Channel kết nối Audio.

Text Messaging & History

Lưu trữ tin nhắn, phân trang lịch sử, infinite scroll

🗄️ Database & Server Layer
A Database Schema
SQL
CREATE TABLE messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    channel_id INTEGER NOT NULL,
    sender_id  INTEGER NOT NULL,
    content    TEXT    NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (channel_id) REFERENCES channels(id) ON DELETE CASCADE,
    FOREIGN KEY (sender_id)  REFERENCES users(id)
);

-- Index tối ưu truy vấn lịch sử (cực kỳ quan trọng khi DB phình to)
CREATE INDEX idx_messages_channel_timestamp
    ON messages (channel_id, created_at DESC);
B Phân trang Cursor-based (Paged History)

Client gửi: { channel_id, limit: 50, before_message_id: 1024 }. Server truy vấn và đảo ngược kết quả theo thứ tự thời gian tăng dần.

SQL — Cursor Pagination
SELECT m.id, m.content, m.created_at, u.username
FROM messages m
JOIN users u ON m.sender_id = u.id
WHERE m.channel_id = ? AND m.id < ?
ORDER BY m.id DESC
LIMIT ?;
🖥️ UI & Client Layer
A Message Log Component

Mỗi tin nhắn gồm: Avatar · Username · Timestamp · Content. Nếu cùng một user gửi liên tiếp trong ~2 phút, tin nhắn được gộp dưới cùng một header (UX Grouping).

B Infinite Scroll / Lazy Loading
1

Mở kênh → gọi channel.history lấy 50 tin mới nhất → auto scroll to bottom.

2

User cuộn lên đầu (Scroll Top == 0) → hiển thị Loading → gọi thêm channel.history với before_message_id.

3

Scroll Anchoring: Tính toán lại vị trí cuộn để giữ nguyên góc nhìn, tránh màn hình bị "giật".

Emoji & Reactions

Unicode emoji, custom emoji theo server, live reaction update

🗄️ Database & Server Layer
A Database Schema
SQL
-- Custom Emoji theo từng Server
CREATE TABLE custom_emojis (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    server_id INTEGER NOT NULL, name TEXT NOT NULL,
    image_url TEXT NOT NULL,
    FOREIGN KEY (server_id) REFERENCES servers(id) ON DELETE CASCADE
);

-- Bảng Reactions (khoá chính kép ngăn thả trùng)
CREATE TABLE reactions (
    message_id  INTEGER NOT NULL,
    user_id     INTEGER NOT NULL,
    emoji_type  TEXT CHECK(emoji_type IN ('unicode', 'custom')) NOT NULL,
    emoji_value TEXT NOT NULL,
    PRIMARY KEY (message_id, user_id, emoji_value)
);
B Live Update Events
📡 reaction.broadcast_update
{
  "event": "reaction.broadcast_update",
  "data": {
    "message_id": 1024, "emoji_value": "😀",
    "count": 5, "action": "add", "user_id": 14
  }
}
🖥️ UI & Client Layer
A Emoji Picker Component

Pop-up phân chia 2 vùng: Unicode (theo tab: Smileys, Animals, Food…) và Custom Emoji của Server hiện tại.

B Render Inline :name:

C Reaction Badges UI
🖱️ Hover Toolbar

GIFs

Tích hợp Tenor/Giphy API, tìm kiếm và gửi ảnh động

🗄️ Database & Server Layer
A Bảo mật API Key
🔒
Nguyên tắc: Tuyệt đối không hard-code API Key vào mã nguồn. Lưu trong file .env hoặc JSON/YAML bảo mật phía Server. Khi khởi động, Server đọc vào RAM.
B Lưu trữ — message_attachments

Server không tải GIF về máy chủ. GIF được lưu là CDN URL trực tiếp từ Tenor/Giphy trong bảng message_attachments.

SQL
CREATE TABLE message_attachments (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    message_id INTEGER NOT NULL,
    kind       TEXT CHECK(kind IN ('image', 'file', 'gif')) NOT NULL,
    url        TEXT NOT NULL,
    FOREIGN KEY (message_id) REFERENCES messages(id) ON DELETE CASCADE
);
🖥️ UI & Client Layer
A GIF Picker Component
🔥 Trending
Mở picker → tự động load danh sách Trending GIFs đang thịnh hành.
🔍 Search + Debounce
Gõ từ khoá → đợi 300ms (debounce) → gọi endpoint tìm kiếm Tenor/Giphy API.
B Cơ chế Gửi GIF

Client không gửi file ảnh — chỉ đóng gói CDN URL vào sự kiện message.send qua Control Channel.

C Tối ưu Render

Giới hạn chiều rộng tối đa 300px. Nâng cao: hiển thị ảnh tĩnh preview trước, chỉ load GIF động khi người dùng hover/click để tiết kiệm RAM và CPU.

Replies

Trả lời tin nhắn, self-referencing FK, Jump to Message

🗄️ Database & Server Layer
A Self-referencing Schema
SQL
-- Thêm trường reply_to_id vào bảng messages
ALTER TABLE messages
    ADD COLUMN reply_to_id INTEGER REFERENCES messages(id) ON DELETE SET NULL;

CREATE INDEX idx_messages_reply_to ON messages (reply_to_id);
💡
ON DELETE SET NULL: Khi tin nhắn gốc bị xóa, tin nhắn phản hồi vẫn tồn tại — chỉ mất đi mối liên kết (field = NULL), không bị đứt gãy luồng chat.

      "id": 1024, "sender_username": "nguyen_van_A",

  }

🖥️ UI & Client Layer
A Reply Bar tại Composer

Forwarding

Chuyển tiếp tin nhắn, sao chép dữ liệu phía Server

A Thêm trường forwarded_from_id
SQL
ALTER TABLE messages
    ADD COLUMN forwarded_from_id INTEGER REFERENCES messages(id) ON DELETE SET NULL;
CREATE INDEX idx_messages_forwarded_from ON messages (forwarded_from_id);
B Quy trình Server-Side Duplication
1

Xác thực quyền: Kiểm tra user có quyền đọc kênh nguồn và quyền gửi tại kênh đích.

2

Sao chép dữ liệu: Server truy vấn toàn bộ content và attachments của tin nhắn gốc.

3

Tạo bản ghi mới: INSERT vào messages với sender_id = người chuyển tiếp, forwarded_from_id = ID gốc.

4

Sao chép đính kèm (nếu có) và Broadcast tới kênh đích qua channel_routing_map.

A Forward Target Picker Modal

Pop-up giữa màn hình gồm: thanh Live Filter, danh sách phân loại (Recent DMs / Text Channels), nút Send kế bên mỗi đích — có thể gửi tới nhiều đích cùng lúc.

Direct Messages (DMs)

Hội thoại riêng tư, Unified Channel Concept, tái sử dụng code

🗄️ Database & Server Layer
A Unified Channel Concept

DM được coi là một Channel với các đặc tính: server_id = NULL, type = 'dm', chỉ có đúng 2 thành viên.

B Get-or-Create DM Room
SQL — Kiểm tra phòng DM đã tồn tại chưa
SELECT channel_id FROM dm_memberships
WHERE user_id IN (?, ?)
GROUP BY channel_id
HAVING COUNT(DISTINCT user_id) = 2;

Nếu CÓ → trả về channel_id. Nếu CHƯA → Transaction: tạo channel mới + INSERT 2 bản ghi dm_memberships → trả về channel_id mới.

🖥️ UI & Client Layer
A Tab Home — DM List

Icon Home ở Left Server Rail → cột thứ 2 chuyển thành danh sách DM gần đây, mỗi mục gồm: Avatar + Username + Presence dot (Online/Offline).

B Code Reusability
Điểm mạnh: Backend đồng nhất → tầng UI tái sử dụng gần 100% code render của luồng chat. Điểm khác biệt duy nhất: Top Bar hiển thị @nguyen_van_B thay vì #thao-luan-chung, kèm trạng thái kết nối.

Attachments

Upload file, REST API, conditional rendering theo loại file

🗄️ Database & Server Layer
A Database Schema
SQL
CREATE TABLE message_attachments (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    message_id INTEGER NOT NULL,
    filename   TEXT    NOT NULL,
    kind       TEXT CHECK(kind IN ('image', 'file', 'gif')) NOT NULL,
    url        TEXT    NOT NULL,
    file_size  INTEGER NOT NULL,
    FOREIGN KEY (message_id) REFERENCES messages(id) ON DELETE CASCADE
);
B POST /upload — Endpoint độc lập
1

Xác thực: Kiểm tra session_token trong HTTP Header.

2

Validation: Đảm bảo file ≤ 25MB và đúng định dạng cho phép.

3

Lưu trữ: Đổi tên file thành UUID tránh trùng → lưu Local/Cloud Storage.

4

Phản hồi: Trả về 200 OK + JSON chứa file_url, filename, file_size.

🖥️ UI & Client Layer
A Async Upload Flow

Chọn file → ngay lập tức gửi POST /upload ngầm → hiển thị Progress Bar (via onUploadProgress) → nhận file_url → đưa vào hàng đợi Composer.

B Conditional Rendering
🖼️ kind = 'image' / 'gif'
Render inline qua thẻ <img> với max-width/height. Click → mở Lightbox toàn màn hình + nút tải về.
📄 kind = 'file'
Dựng Download Card bo góc: icon định dạng (PDF đỏ, ZIP vàng…) + tên file + dung lượng (vd: 1.0 MB) + nút Download.

Presence & Typing

Trạng thái Online/Idle/Offline, chỉ báo đang gõ thời gian thực

🗄️ Database & Server Layer
A Presence — In-memory Only

Trạng thái hoạt động không ghi vào SQLite (tránh nghẽn I/O). Toàn bộ lưu trên RAM.

C++
enum class UserStatus { Online, Idle, Offline };

struct UserPresence {
    UserStatus status;
    int64_t    last_active_timestamp;
};

std::unordered_map<int, UserPresence> global_presence_map;
🟢 Online
Khi WebSocket kết nối thành công và xác thực → cập nhật RAM → broadcast presence.update tới tất cả Server thành viên.
🟠 Idle
Không tương tác trong 5-10 phút → Heartbeat Timer kích hoạt → chuyển Idle → broadcast cập nhật.
⚫ Offline
Socket ngắt kết nối → giữ Grace Period 30 giây (phòng mạng chập chờn) → sau đó broadcast Offline chính thức.
B Typing — Transient Event

Server nhận typing.start chứa channel_id → trích xuất user_id → dùng channel_routing_map gửi tới các thành viên khác. Không lưu trữ. Nếu sau 4 giây không nhận thêm gói mới → tự coi như đã dừng gõ.

🖥️ UI & Client Layer
A Client Throttling
Typing Throttling: Gõ ký tự đầu → gửi ngay typing.start → khóa 3 giây → dù gõ thêm bao nhiêu cũng không gửi thêm → hết khóa → gửi tiếp nếu vẫn đang gõ.
B Typing Indicator UI
✍️ Hiển thị
"Nguyễn Văn A đang gõ…" | "A, B, C đang gõ…" | "Nhiều người đang gõ…" kèm animation 3 chấm nhấp nhô.
⏱️ Timeout 4s
Mỗi sự kiện nhận được đặt bộ đếm 4 giây. Không nhận mới → tự xóa tên khỏi danh sách đang gõ.
C Presence Dots UI

Chấm tròn màu đè lên góc dưới phải Avatar ở tất cả vị trí trong app:

Xanh lá — Trực tuyến (Online)
Cam/Vàng — Treo máy (Idle)
Xám — Ngoại tuyến (Offline)
