Kiến Trúc Dữ Liệu & Mô Hình Xử Lý Đa Luồng

Tài liệu phân tích kỹ thuật hệ thống kết hợp SQL Server, Redis, SQLite và WebRTC

1. Chiến lược phân tầng dữ liệu (Database Layering)

Hệ thống kết hợp đồng thời cả 3 giải pháp lưu trữ dữ liệu để tối ưu hóa hiệu năng toàn diện:

SQL Server (RDBMS)
Bản chất kỹ thuật: Hệ quản trị cơ sở dữ liệu quan hệ (Relational), lưu trữ xuống đĩa cứng (Disk) theo cấu trúc bảng có ràng buộc nghiêm ngặt (PK, FK). Tuân thủ chặt chẽ tính chất ACID để đảm bảo dữ liệu an toàn khi mất điện đột ngột.
Định nghĩa đơn giản: Giống như "Sổ cái tài chính" của công ty.
Ứng dụng: Lưu dữ liệu cực kỳ quan trọng, cần lưu vĩnh viễn và không được sai sót (Tài khoản, mật khẩu hash, lịch sử giao dịch, bạn bè).
Redis (In-Memory Database)
Bản chất kỹ thuật: Cơ sở dữ liệu dạng Key-Value (Khóa - Giá trị) lưu trữ hoàn toàn trên RAM. Tốc độ đọc/ghi nhanh hơn đĩa cứng hàng ngàn lần, xử lý hàng trăm ngàn requests/s với độ trễ < 1ms. Mất điện sẽ mất sạch dữ liệu nếu không cấu hình AOF/RDB.
Định nghĩa đơn giản: Giống như "Bảng ghi nhớ (Sticky Notes)" trên bàn làm việc.
Ứng dụng: Lưu dữ liệu cần truy cập siêu nhanh, thay đổi liên tục (Trạng thái online/offline, Session token, phòng chat tạm thời).
SQLite (Embedded Database)
Bản chất kỹ thuật: Thư viện cơ sở dữ liệu độc lập, chạy dạng Serverless (không có tiến trình Server riêng) mà được nhúng thẳng vào file chạy (.exe) của ứng dụng Client (Qt/C#). Toàn bộ DB gói gọn trong 1 file duy nhất trên máy người dùng.
Định nghĩa đơn giản: Giống như "Sổ tay cá nhân" của Client.
Ứng dụng: Lưu dữ liệu cục bộ nhằm giảm tải cho Server (Lịch sử tin nhắn cũ để mở app lên là thấy ngay, cài đặt Dark/Light mode, cache avatar).

2. Đồng bộ hóa dữ liệu: Cơ chế Cache Aside Pattern

Để giải quyết bài toán dữ liệu giữa Redis và SQL Server không bị xung đột hoặc lệch nhau, hệ thống áp dụng mô hình Cache Aside:

Quy trình Đọc dữ liệu (Read):

  1. Đọc từ Redis trước: Nếu tìm thấy dữ liệu (Cache Hit), trả về ngay lập tức cho Client.
  2. Đọc từ SQL Server nếu thiếu: Nếu không thấy dữ liệu ở Redis (Cache Miss), Server sẽ truy vấn vào SQL Server → Trả dữ liệu cho Client → Đồng thời ghi ngược dữ liệu đó vào Redis kèm thời gian hết hạn (TTL - Time To Live).

Quy trình Cập nhật dữ liệu (Update):

  • Khi người dùng thay đổi thông tin (ví dụ: đổi tên), Server sẽ ghi tên mới vào SQL Server đầu tiên, sau đó thực hiện xóa (hoặc cập nhật) Key tương ứng trong Redis để tránh việc Client đọc phải dữ liệu cũ đã lỗi thời.

3. WebRTC & Giao thức ICE (Web Real-Time Communication)

WebRTC là một tập hợp các tiêu chuẩn và giao thức (gồm SRTP mã hóa media, SCTP truyền dữ liệu, STUN/TURN đục tường lửa) phối hợp với nhau nhằm thiết lập kết nối trực tiếp Peer-to-Peer (P2P) giữa hai Client mà không cần đi qua Server.

Cơ chế thiết lập kết nối qua ICE (Interactive Connectivity Establishment):

  1. Thu thập ứng viên (Candidate): Client A tự kiểm tra tất cả các đường có thể kết nối mạng của mình (IP nội bộ, IP công cộng qua STUN, IP qua TURN). Mỗi đường kết nối này gọi là một ICE Candidate.
  2. Trao đổi SDP (Session Description Protocol): Hai bên gửi cho nhau một file văn bản chứa thông tin về codec âm thanh/hình ảnh hỗ trợ và danh sách các ICE Candidate vừa tìm được. Quá trình này gọi là Signaling (thường chạy qua Socket TCP của C++ Asio Server).
  3. Kiểm tra kết nối (Connectivity Checks): Hai bên thử bắt tay nhau qua các Candidate. Đường mạng nào ngắn nhất, nhanh nhất và không bị tường lửa chặn sẽ được chọn để truyền Voice/Video. Nếu thất bại hoàn toàn, hệ thống mới chuyển sang đi qua đường TURN của Coturn.

4. Mô hình xử lý bất đồng bộ trong C++ Asio: io_context & Thread Pool

Để đảm bảo backend C++ có thể xử lý hàng ngàn Client nhắn tin và gọi điện cùng lúc, cơ chế điều khiển luồng dựa vào trung tâm là đối tượng asio::io_context (một Event Loop - Vòng lặp sự kiện).

Khi các thao tác mạng bất đồng bộ được đẩy xuống tầng OS và xử lý xong, OS sẽ ném các hàm xử lý kết quả (Completion Handlers/Callbacks) vào một hàng đợi (Queue) nằm trong io_context. Để xử lý các Callback này, ta cần gọi hàm io_context.run() theo một trong hai mô hình:

Mô hình Cơ chế hoạt động Ưu / Nhược điểm
Single-Thread (Đơn luồng) Gọi io_context.run() ngay trong hàm main. Toàn bộ sự kiện mạng được xử lý tuần tự trên 1 luồng duy nhất. ✔ An toàn, không sợ xung đột dữ liệu (Thread-safety).
✘ Không tận dụng được CPU đa nhân.
Multi-Thread / Thread Pool (Đa luồng) Tạo ra một nhóm gồm $N$ luồng (thường bằng số nhân CPU) và luồng nào cũng gọi io_context.run(). Các luồng cùng nhảy vào hàng đợi để nhặt việc ra làm song song. ✔ Tận dụng tối đa hiệu năng phần cứng đa nhân.
✘ Rủi ro xung đột dữ liệu (Race Condition).
LƯU Ý CHÍ MẠNG KHI DÙNG THREAD POOL: Vì các hàm Callback có thể chạy đồng thời trên các luồng khác nhau, nếu hai luồng cùng lúc sửa đổi dữ liệu phòng chat hoặc ghi dữ liệu vào SQL Server, bạn bắt buộc phải dùng Mutex (std::mutex) hoặc cơ chế Strand (asio::strand) của Asio để xếp hàng các tác vụ, tránh làm hỏng bộ nhớ (Race Condition).

5. Thiết kế dữ liệu lưu trong SQL Server

Dưới đây là các phân hệ dữ liệu lõi cần được lưu trữ vĩnh viễn và đảm bảo ràng buộc chặt chẽ trong SQL Server:

5.1. Phân hệ Quản lý Tài khoản (User Management)

Dữ liệu định danh người dùng cần bảo mật và kiểm tra ràng buộc duy nhất (Unique).

Bảng: Users (Người dùng)

Tên cột (Column Name) Kiểu dữ liệu Ràng buộc / Ghi chú
UserID INT Primary Key, Identity (Mã định danh duy nhất của user)
Username VARCHAR(50) Unique (Tên đăng nhập)
PasswordHash VARCHAR(255) Mật khẩu đã được băm kèm Salt (BCrypt/SHA-256). Tuyệt đối không lưu mật khẩu thô.
DisplayName NVARCHAR(100) Tên hiển thị (Hỗ trợ tiếng Việt có dấu)
AvatarURL VARCHAR(255) Đường dẫn tới file ảnh đại diện
CreatedAt DATETIME Thời gian tạo tài khoản

Bảng: Friendships (Mối quan hệ bạn bè)

Tên cột (Column Name) Kiểu dữ liệu Ràng buộc / Ghi chú
UserSrcID INT Foreign Key (ID người gửi lời mời)
UserDstID INT Foreign Key (ID người nhận lời mời)
Status TINYINT 0: Đang chờ duyệt, 1: Đã là bạn bè, 2: Đã chặn/Block
UpdatedAt DATETIME Thời gian cập nhật trạng thái gần nhất

5.2. Phân hệ Tin nhắn (Messaging System)

Mặc dù Client có SQLite để đọc offline, SQL Server vẫn cần lưu toàn bộ lịch sử để phục vụ việc đồng bộ khi người dùng đăng nhập thiết bị mới.

Bảng: Channels / Groups (Phòng Chat/Nhóm Chat)

Tên cột Kiểu dữ liệu Ràng buộc / Ghi chú
ChannelID INT Primary Key, Identity
ChannelName NVARCHAR(100) Nullable (Nếu là chat đôi 1-1 thì để trống)
IsGroup BIT 0 nếu là chat đôi, 1 nếu là chat nhóm nhiều người
InviteCode VARCHAR(20) Unique, Nullable (Chuỗi mã ngẫu nhiên phục vụ tính năng vào nhóm cố định)
IsLinkInviteEnabled BIT 1: Cho phép vào bằng link, 0: Khóa tính năng
CreatedAt DATETIME Ngày tạo phòng

Bảng: ChannelMembers (Thành viên phòng chat)

* Ghi chú: Khóa chính (Primary Key) là sự kết hợp của cả 2 cột (ChannelID, UserID).

Tên cột Kiểu dữ liệu Ràng buộc / Ghi chú
ChannelID INT Foreign Key từ bảng Channels
UserID INT Foreign Key từ bảng Users
Role TINYINT 0: Thành viên, 1: Trưởng nhóm/Admin

Bảng: Messages (Lịch sử tin nhắn text)

Tên cột Kiểu dữ liệu Ràng buộc / Ghi chú
MessageID BIGINT Primary Key, Identity (Dùng BIGINT đề phòng số lượng tăng nhanh)
ChannelID INT Foreign Key
SenderID INT Foreign Key
MessageType TINYINT 0: Text thuần túy, 1: Hình ảnh, 2: File đính kèm
EncryptedContent VARBINARY(MAX) / TEXT Nội dung tin nhắn đã được mã hóa lai (RSA + AES). Server chỉ lưu chứ không thể đọc nội dung gốc.
Timestamp DATETIME Thời gian tin nhắn được ghi nhận tại Server

5.3. Phân hệ Nhật ký Cuộc gọi (Call Log)

Phục vụ tính năng hiển thị lịch sử cuộc gọi (Voice/Video) trên giao diện Qt/C# của Client.

Bảng: CallLogs

Tên cột Kiểu dữ liệu Ràng buộc / Ghi chú
CallID VARCHAR(50) Primary Key (Chuỗi GUID ngẫu nhiên sinh ra khi bắt đầu cuộc gọi)
CallerID INT Foreign Key (Người chủ động gọi)
CalleeID INT Foreign Key (Người nhận cuộc gọi - Nếu gọi nhóm cần thiết kế bảng liên kết riêng)
CallType TINYINT 0: Cuộc gọi Voice, 1: Cuộc gọi Video
StartTime DATETIME Thời gian bắt đầu kết nối thành công
EndTime DATETIME Nullable (Thời gian gác máy)
Status TINYINT 0: Gọi nhỡ/Missed, 1: Thành công/Connected, 2: Máy bận/Busy, 3: Từ chối/Rejected

6. Dữ liệu TUYỆT ĐỐI KHÔNG LƯU trong SQL Server (Đẩy sang Redis)

Để Server C++ không bị nghẽn cổ chai I/O do giới hạn tốc độ đọc ghi đĩa cứng của RDBMS, các loại dữ liệu thay đổi liên tục hoặc tạm thời sau đây bắt buộc phải lưu trên RAM của Redis:

  • Trạng thái Online/Offline (User Status): User bật/tắt app hoặc mất mạng liên tục, nếu update vào SQL Server sẽ gây quá tải đĩa. Lưu ở Redis dưới dạng: Key: User:123:Status -> Value: "Online".
  • Mã Token phiên làm việc (Session Token/JWT): Dùng để xác thực liên tục mỗi khi Client gửi request hoặc chat. Lưu ở Redis giúp truy vấn tốc độ cao < 1ms.
  • Tín hiệu bắt tay WebRTC (SDP / ICE Candidates tạm thời): Quá trình trao đổi diễn ra rất nhanh trong vài giây rồi bỏ. Nên dùng cơ chế Pub/Sub của Redis hoặc lưu tạm trên RAM để chuyển tiếp, không lưu vào ổ cứng.
  • Link/Mã mời tham gia phòng chat tạm thời (Có thời hạn): Lưu bằng tính năng tự hủy TTL (Time-to-Live) của Redis.
    Ví dụ: Key: invite:code:xyz123 | Value (JSON): {"ChannelID": 102, "InviterID": 5, "Type": "Group"} | Expire: 300 giây (5 phút).

7. Quy trình Tính năng "Mời vào nhóm bằng Link & QR Code"

7.1. Bước 1: Phía Người mời (Tạo Link & QR)

  1. Client gửi yêu cầu "Tạo link mời" lên C++ Server qua Socket.
  2. Server sinh chuỗi ngẫu nhiên không trùng lặp (ví dụ mã hóa chuỗi 8 ký tự: aB8fX2qZ).
  3. Server lưu chuỗi vào SQL Server (nếu vĩnh viễn) hoặc Redis (nếu tạm thời kèm TTL).
  4. Server trả chuỗi về cho Client dưới dạng một URL hoàn chỉnh sử dụng Deep Link/Custom Protocol: myapp://join/aB8fX2qZ. Hệ điều hành sẽ tự mở app khi bấm link thay vì mở trình duyệt.
  5. Tạo QR Code tại máy Client: Để tiết kiệm băng thông Server, Client tự biến chuỗi URL thành ảnh QR:
    • Nếu dùng C#: Tích hợp thư viện QRCoder.
    • Nếu dùng Qt (C++): Tích hợp thư viện QrCodeGenerator.

7.2. Quy trình Xử lý khi Người nhận quét QR hoặc bấm Link

[ Người nhận bấm Link / Quét QR ] | v (Trích xuất chuỗi mã) ---> Ví dụ lấy được: "aB8fX2qZ" | v [ Client gửi mã lên C++ Server ] | v [ Server kiểm tra tính hợp lệ ] - Bước A: Tìm trong Redis (Link tạm thời) -> Nếu có, lấy ChannelID. - Bước B: Tìm trong SQL Server (Link nhóm) -> Nếu có, lấy ChannelID + Kiểm tra tính năng cho phép vào bằng link. | v (Mã hợp lệ không?) / \ (Có) (Không/Hết hạn) ---> Báo lỗi về Client | v [ Thực hiện Logic Tham Gia ] 1. Thêm User vào bảng `ChannelMembers` trong SQL Server. 2. Server gửi thông báo qua Socket tới toàn bộ thành viên cũ: "User X đã tham gia phòng bằng Link". 3. Trả về giao diện phòng chat mới cho Client vừa vào.
LƯU Ý NÂNG CAO VỀ BẢO MẬT:
  • Chống Spam/Dò mã (Brute-force): Mã mời (InviteCode) phải có độ dài tối thiểu từ 8-12 ký tự bao gồm cả chữ hoa, chữ thường và chữ số.
  • Tính năng phê duyệt (Pending Approval): Với nhóm bảo mật cao, khi người dùng bấm link, hãy chuyển trạng thái của họ vào danh sách chờ trong SQL Server. Đồng thời gửi một Notification qua Socket đến Admin nhóm: "User B muốn vào nhóm bằng link của bạn, bạn có đồng ý không?". Khi Admin bấm duyệt, Server mới thêm vào bảng ChannelMembers.
